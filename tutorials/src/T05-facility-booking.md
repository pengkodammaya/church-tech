# What you are building

Members open a page, pick a room and date, see which time slots are free, and submit a
request. The church office sees pending requests and approves or rejects them. Approved
slots lock.

New idea this time: a **database**. The schedule in T04 was one file; bookings change
constantly and are shared by many people, so they live in a proper hosted database —
**Supabase** (free tier, built on PostgreSQL).

```
Member page ──▶ POST /api/bookings ──▶ Supabase table
Office page ──▶ PATCH /api/bookings/id ─▶ approve / reject
Conflict check: same room+date+slot already pending/approved? → refuse politely
```

> This is the take-home tutorial: it has more moving parts than anything on the day.
> Budget a relaxed 2–3 hours. Nothing here is conceptually hard; there is just more of it.

# Part A — Supabase setup (browser only)

1. `https://supabase.com` → Start your project → sign in with GitHub → New project:
   name `church-facility`, pick a region near you, generate a database password and
   store it safely (you will not need it daily, but keep it).
2. Wait ~2 minutes for provisioning.
3. Left sidebar → **SQL Editor** → New query. Paste ALL of `schema.sql` below and Run:

```sql
create table if not exists bookings (
  id bigint generated by default as identity primary key,
  room text not null,
  booking_date date not null,
  slot text not null,
  name text not null,
  email text not null,
  notes text,
  status text not null default 'pending',
  created_at timestamptz not null default now()
);

create index if not exists bookings_room_date_idx on bookings (room, booking_date);
```

4. Project Settings → **API**: copy two values —
   - **Project URL** (like `https://abcd.supabase.co`)
   - **service_role key** (long string)

> The service_role key bypasses all row-level security. It lives ONLY on the server
> side (Vercel env vars), never in browser code, never in git. If it ever leaks,
> rotate it in Supabase immediately.

# Part B — Build the app

```powershell
mkdir facility-booking
cd facility-booking
opencode
```

## Prompt 1 — scaffold

```
Create a minimal Next.js JavaScript app (App Router) that will be a facility booking
system. Just a working skeleton with a home page heading "Facility Booking".
```

## Prompt 2 — rooms and slots

```
Create lib/rooms.js exporting ROOMS: Main Hall (200 pax, worship services and large
events), Function Room (40, meetings and cell groups), Kitchen (10, event catering);
and SLOTS: five 2-hour blocks from 09:00 to 21:00 like "09:00-11:00", skipping lunch
13:00-14:00. Also todayISO() returning today as YYYY-MM-DD local date.
```

## Prompt 3 — public booking page

```
Home page (client component): dropdown for room, date picker defaulting to today,
then a card grid of the five slots. For each slot show Free + Request button, or
Booked/Pending taken from fetched data. Below, inputs for name, email, purpose,
and a status message area. Fetch existing bookings from GET /api/bookings?room=&date=
whenever room or date changes.
```

## Prompt 4 — API with conflict checking

```
Create lib/supabase.js exporting getSupabase() using @supabase/supabase-js with
SUPABASE_URL and SUPABASE_SERVICE_KEY env vars, throwing a helpful error if missing.

app/api/bookings/route.js:
- GET: list bookings, optional room/date filters, exclude rejected, sorted by date.
- POST: validate required fields room,date,slot,name,email; check no existing
  non-rejected booking for same room+date+slot, else 409 with friendly message;
  insert with status pending; return created record.

All DB access server-side only. Add .env.local support via .env.example too.
```

Test: run `npm run dev`, request a free slot → success message; request the same slot
again → polite refusal. That refusal IS the conflict checker earning its keep.

[SCREENSHOT: slot grid showing one pending and refusal message]

## Prompt 5 — office approval page

```
Create /admin page: password input for ADMIN_PASSCODE, then fetch GET /api/bookings
(all). List pending requests each with Approve and Reject buttons calling PATCH
/api/bookings/[id] sending {status:"approved"|"rejected"} and header x-admin-passcode.
Show history below. Keep styling consistent.
```

Add the PATCH route (let opencode create `app/api/bookings/[id]/route.js`) which checks
`checkAdmin(request)` against `ADMIN_PASSCODE` before updating.

Fill `.env.local` with your three values from Part A plus any passcode you invent.
Restart dev server. Book → approve → reload member page → slot now shows **Booked**.
The full loop works locally.

# Part C — Deploy

1. GitHub repo (`github.com/new`), then ask opencode to init/commit/push.
2. `vercel.com/new` → import → set Environment Variables BEFORE first deploy if possible:
   `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `ADMIN_PASSCODE`.
3. Deploy, open live URL, repeat the book→approve loop in production.

# Honest limitations of this MVP

| Limitation | Why it is OK for now | Upgrade path |
|---|---|---|
| Single shared passcode | Office team is small | Supabase Auth logins later |
| Fixed 2-hour blocks | Matches how halls are actually used | Per-room slot config |
| No notification on approve | Manual courtesy call works | Resend email on status change (reuse T04 skill!) |
| Anyone can request | Requests still need approval | Rate-limit/captcha if abused |

# Stretch goals

1. Email the requester when approved (you know how to send email now).
2. Block past dates: reject POSTs where `date < today`.
3. Recurring booking ("every Friday for 8 weeks") — loop inserts with conflict checks.
4. Public embed of upcoming approved bookings on the main church site.

When someone asks "can it also do equipment/talent/schedules?" — the answer is yes:
same pattern (table + API routes + pages), different fields. You have learned the shape.
